O que é uma API?
API significa Application Programming Interface — em português, Interface de Programação
de Aplicações. É um contrato que define como um software pode pedir coisas a outro software,
e o que ele vai receber de volta.
Toda vez que você abre o app do clima, paga com Pix, faz login com o Google ou vê um mapa dentro do app
de delivery, há APIs trabalhando nos bastidores. Elas são a "cola" que conecta sistemas diferentes, escritos em
linguagens diferentes, rodando em computadores diferentes — às vezes em continentes diferentes.

🍽️ Analogia: o restaurante
Você (o cliente) não entra na cozinha, não sabe a receita e nem precisa saber quem é o cozinheiro. Você
olha o cardápio (a documentação da API), faz um pedido dentro das regras (a requisição) e o garçom (a
API) traz o prato (a resposta). Se pedir algo que não está no cardápio, o garçom diz "não temos" (um erro
404). Se a cozinha pegar fogo, ele diz "estamos com problemas" (um erro 500).

Definição formal
📘 Definição
Uma API é um conjunto de regras, protocolos e definições que permite que dois componentes de
software se comuniquem. Ela especifica quais operações estão disponíveis, como chamá-las (formato da
requisição), o que esperar de volta (formato da resposta) e quais erros podem acontecer.

Uma breve história das APIs
As APIs nasceram muito antes da internet que conhecemos. Elas evoluíram de chamadas de
funções dentro de um mesmo computador até ecossistemas globais consumidos por bilhões de
dispositivos — e agora, por agentes de inteligência artificial.
🤓 Curiosidade: o "mandato das APIs" de Bezos
Por volta de 2002, segundo relato famoso de um ex-engenheiro, Jeff Bezos teria determinado que todas
as equipes da Amazon deveriam expor seus dados e funcionalidades somente por meio de interfaces de
serviço — sem acesso direto ao banco de dados de outro time. Quem não cumprisse seria demitido. Essa
cultura "API-first" é apontada como uma das sementes da AWS.
1968 O termo "application program interface" aparece em um artigo acadêmico sobre computação gráfica
remota. A ideia: separar o que um módulo faz de como ele faz.
Anos 80–90 APIs de sistemas operacionais e bibliotecas dominam: POSIX (1988), Win32. Surgem tecnologias
de objetos distribuídos como CORBA (1991), DCOM e Java RMI — poderosas, mas complexas.
1998 Nasce o XML-RPC, que evolui para o SOAP. Começa a era dos Web Services corporativos, com XML e
contratos WSDL.
2000 Roy Fielding descreve o estilo arquitetural REST em sua tese de doutorado. No mesmo ano, Salesforce e
eBay lançam algumas das primeiras APIs web comerciais.
2002–2006 Amazon lança seus primeiros web services (2002). Flickr (2004), Google Maps (2005) e Twitter
(2006) abrem APIs e surge a "era dos mashups". Em 2006, a AWS lança S3 e EC2: infraestrutura inteira via API.
2007–2010 Facebook Platform, iPhone e App Store: os smartphones explodem e todo app precisa de um
back-end. APIs REST + JSON viram padrão.
2011 Criado o Swagger, para descrever APIs REST de forma legível por máquinas.
2015 Ano agitado: Facebook publica o GraphQL, Google publica o gRPC, o HTTP/2 é padronizado e o Swagger
é doado para a recém-criada OpenAPI Initiative.
2017 Lançada a especificação OpenAPI 3.0. Arquiteturas de microsserviços e API Gateways se popularizam.
2020–2021 No Brasil, o Pix estreia (nov/2020) e o Open Banking, depois Open Finance Brasil, começa em
2021: bancos são obrigados a compartilhar dados via APIs padronizadas, com consentimento do cliente. Sai o
OpenAPI 3.1.
2022–2023 HTTP/3 é padronizado (RFC 9114). A OWASP atualiza o API Security Top 10 (2023). APIs de
modelos de linguagem (LLMs) se tornam um dos produtos mais consumidos do planeta.
2024–hoje Surge o MCP (Model Context Protocol), que padroniza como agentes de IA descobrem e usam
ferramentas e APIs. As APIs passam a ter um novo tipo de consumidor: máquinas que raciocinam.

🤓 HTTP/1.1, HTTP/2 e HTTP/3
O HTTP/1.1 (1997) é texto puro e envia uma requisição por vez em cada conexão. O HTTP/2 (2015) é
binário e multiplexa várias requisições na mesma conexão. O HTTP/3 (2022) troca o TCP pelo QUIC
(sobre UDP), reduzindo a latência em redes instáveis, como o 4G no ônibus. Para quem usa a API, a
semântica (métodos, status, headers) é a mesma.
⚠️ HTTP × HTTPS
HTTP puro trafega tudo em texto aberto: qualquer um na mesma rede Wi-Fi pode ler senhas e tokens.
HTTPS = HTTP + TLS (criptografia). Em APIs, HTTPS não é opcional: é obrigatório.

Seguro e idempotente: duas palavras que valem ouro
🛡️ Seguro (safe)
O método não altera nada no servidor. É "só
olhar". GET, HEAD e OPTIONS são seguros. Por
isso navegadores, crawlers e caches podem
repeti-los à vontade.
🔁 Idempotente
Fazer a mesma chamada 1 vez ou 100 vezes
deixa o servidor no mesmo estado final. DELETE
/livros/7 repetido continua com o livro 7
apagado. Já POST /pedidos repetido cria 100
pedidos!
🍽️ Analogia: o botão do elevador
Apertar o botão do 5º andar uma vez ou dez vezes (com impaciência) tem o mesmo efeito: o elevador vai
ao 5º andar. Isso é idempotência. Agora imagine a máquina de café: cada aperto sai um café novo (e
uma cobrança nova). Isso é um POST. É por isso que, quando a rede falha, é seguro repetir um PUT, mas
repetir um POST de pagamento pode cobrar o cliente duas vezes.

401 ou 403? A dúvida mais comum
🍽️ Analogia: a balada
401 é o segurança na porta dizendo: "Cadê seu documento?" — você ainda não provou quem é. 403 é
quando você mostra o documento, ele confere e diz: "Ok, você é o João... mas não está na lista VIP."
Identificado, mas sem permissão.
Escolhendo o código certo
Criou algo com POST? Use 201 e devolva o cabeçalho Location .
Apagou com DELETE e não há nada para devolver? 204.
JSON mal formado? 400. JSON válido, mas com e-mail inválido? 422 (ou 400, se sua API preferir simplificar
— o importante é ser consistente).
Tentou criar um usuário com e-mail já cadastrado? 409.
Processamento demorado (gerar um relatório)? 202 + um link para consultar o andamento.
⚠️ O anti-padrão do "200 com erro"
Responder 200 OK com o corpo {"sucesso": false, "erro": "Usuário não encontrado"} engana
proxies, caches, monitoramento e as bibliotecas dos clientes, que acham que deu tudo certo. Use o
código HTTP adequado.
🤓 Curiosidade: 418 I'm a teapot ☕
O código 418 ("Eu sou um bule de chá") nasceu como piada de 1º de abril em 1998, na RFC 2324 (o
"protocolo de controle de cafeteiras"). Ele virou tão querido que, quando tentaram removê-lo de
bibliotecas populares, a comunidade protestou. Hoje ele é reservado e não deve ser usado para outra
coisa.

Cliente e servidor precisam concordar não só no "como pedir", mas no formato dos dados. O
cabeçalho Content-Type diz qual formato está sendo usado.
JSON — o rei das APIs modernas
JSON (JavaScript Object Notation) é leve, legível por humanos e suportado por praticamente todas as
linguagens. Tem apenas seis tipos de dados:

💡 Convenções que evitam dor de cabeça
Datas sempre em ISO 8601 com fuso: "2026-10-27T12:00:00Z" ou "2026-10-27T09:00:00-
03:00" .
Dinheiro: evite float (0.1 + 0.2 ≠ 0.3!). Use centavos inteiros ( 14990 ) ou string decimal
( "149.90" ) + a moeda ( "BRL" ).
Nomes de campos: escolha snake_case ou camelCase e seja consistente em toda a API.
IDs grandes como string, porque JavaScript perde precisão acima de 253.

REST a fundo
REST (Representational State Transfer) não é um protocolo nem uma biblioteca: é um estilo
arquitetural, um conjunto de restrições descrito por Roy Fielding em 2000. Uma API que segue
essas restrições é chamada de RESTful.
A ideia central: recursos e representações
Em REST, tudo é um recurso (um cliente, um pedido, uma foto), identificado por uma URI. O que trafega pela
rede não é o recurso em si, mas uma representação do seu estado — geralmente em JSON. Daí o nome:
transferência de estado representacional.
As 6 restrições do REST
↔️
1. Cliente-servidor
Interface e armazenamento são
separados. Cada lado evolui de
forma independente.
🧠
2. Sem estado (stateless)
Cada requisição carrega tudo o que
é necessário (incluindo o token). O
servidor não guarda "sessão" entre
chamadas.
⚡
3. Cacheável
As respostas dizem se podem ser
guardadas em cache, e por quanto
tempo.
📐
4. Interface uniforme
URIs para recursos, verbos
padronizados, mensagens
autodescritivas e hipermídia.
🧅
5. Sistema em camadas
O cliente não sabe se fala com o
servidor final, um cache, um
balanceador ou um gateway.
📦
6. Código sob demanda
(opcional)
O servidor pode enviar código
executável ao cliente (como
JavaScript).
🍽️ Analogia: stateless é o atendente com amnésia
Imagine um atendente de lanchonete que esquece você assim que entrega o pedido. Para pedir de novo,
você precisa mostrar a comanda (o token) toda vez. Parece chato, mas tem uma vantagem enorme:
qualquer atendente pode atender você. É isso que permite colocar 50 servidores idênticos atrás de um
balanceador de carga.

Além do REST
REST é ótimo, mas não é a resposta para tudo. Conheça os outros estilos, quando cada um
brilha e como eles se parecem na prática.
🧼 SOAP — o veterano engravatado
SOAP (Simple Object Access Protocol) usa sempre XML, dentro de um "envelope" padronizado, e é descrito por
um contrato WSDL. É verboso, mas tem padrões robustos de segurança (WS-Security) e transações. Ainda é
comum em bancos, seguradoras e sistemas de governo.
◈ GraphQL — "peça exatamente o que quer"
Criado no Facebook, o GraphQL expõe um único endpoint (geralmente POST /graphql ) e um esquema
tipado. O cliente escreve uma query dizendo exatamente quais campos quer, e recebe uma resposta com o
mesmo formato. Ele resolve dois problemas clássicos do REST:
Over-fetching: o REST devolve 40 campos quando a tela só precisa de 2.
Under-fetching: para montar uma tela, o app precisa de 4 chamadas REST diferentes.
Além de queries (leitura), o GraphQL tem mutations (escrita) e subscriptions (eventos em tempo real). Os
pontos de atenção: o cache HTTP é mais difícil (tudo é POST no mesmo endpoint) e é preciso limitar a
profundidade e o custo das queries para evitar abusos.

⚡ gRPC — velocidade máxima entre serviços
Criado pelo Google, o gRPC permite chamar uma função em outro servidor como se ela fosse local. O contrato

Autenticação e autorização
Duas perguntas que toda API precisa responder em cada requisição: "Quem é você?"
(autenticação) e "O que você pode fazer?" (autorização).
🍽️ Analogia: o hotel
No check-in, você mostra o documento na recepção: isso é autenticação. Em troca, recebe um cartão-
chave (o token). O cartão abre o seu quarto e a academia, mas não o quarto do vizinho nem a sala do
gerente: isso é autorização. E no dia do check-out o cartão para de funcionar: o token expira.
Os métodos mais comuns
🔑 API Key (chave de API)
Uma string secreta que identifica a aplicação (não necessariamente o usuário). Simples e muito usada em APIs
públicas.
👤 HTTP Basic
Envia usuario:senha codificado em Base64. Atenção: Base64 não é criptografia, é só uma codificação
reversível. Só use com HTTPS e, de preferência, apenas em casos simples ou internos.
🎫 Bearer Token e JWT
O cliente faz login uma vez, recebe um token e passa a enviá-lo em todas as chamadas: Authorization:
Bearer <token> . "Bearer" significa "portador": quem tiver o token, tem o acesso — por isso ele deve ser
protegido como uma senha. O formato mais popular de token é o JWT (JSON Web Token):

Por padrão, o navegador impede que JavaScript de app.loja.com leia respostas de api.outrosite.com (é a
Same-Origin Policy). O CORS (Cross-Origin Resource Sharing) é como a API diz ao navegador quais origens
estão autorizadas. Para requisições "não simples", o navegador faz antes uma pergunta, o preflight:
🌐 Navegador (app.loja.com)
🖥️ API (api.loja.com)
1. OPTIONS /pedidos — "Posso fazer um POST daqui?" (preflight)
2. 204 · Access-Control-Allow-Origin: https://app.loja.com
3. POST /pedidos — a requisição de verdade
4. 201 Created ✅
Figura 12.1 — O preflight do CORS. Quem bloqueia é o navegador, não o servidor.
⚠️ CORS não protege sua API
CORS só vale dentro de navegadores. Um script em Python ou o curl ignoram completamente o CORS.
Ele protege os usuários contra sites maliciosos, não substitui autenticação. E evite Access-Control-
Allow-Origin: * em APIs que usam cookies ou dados privados.

🔒 HTTPS em tudo, com TLS 1.2 ou superior.

💉 Queries parametrizadas: nunca concatene

🙈 Nunca coloque tokens ou senhas na URL: elas

🎯 Devolva só os campos necessários (nada de

🗝️ Segredos em cofres (Vault, Key Vault, Secrets

Resiliência: falhar com elegância
⏱️ Timeouts
Toda chamada externa deve ter tempo máximo. Sem
timeout, uma API lenta trava a sua junto.
🔁 Retentativas com backoff
Tente de novo esperando cada vez mais (1s, 2s, 4s...) e
com um pouco de aleatoriedade (jitter), só em operações
idempotentes.
🔌 Circuit breaker
Como o disjuntor de casa: se um serviço falha muito,
"desarma" e para de chamá-lo por um tempo, evitando
efeito cascata.
📨 Processamento assíncrono
Tarefas pesadas vão para uma fila; a API responde 202
Accepted na hora.
💡 Outras otimizações rápidas
Compressão ( Content-Encoding: gzip ou br ), HTTP/2 ou 3, reaproveitamento de conexões,
paginação, seleção de campos e índices no banco de dados. Meça antes de otimizar: a lentidão quase
sempre está em uma consulta ao banco.
RETENTATIVA COM BACKOFF EXPONENCIAL + JITTER
async function comRetentativas(fn, tentativas = 5) {
for (let i = 0; i < tentativas; i++) {
try {
return await fn();
} catch (erro) {
if (i === tentativas - 1) throw erro;
const espera = Math.min(1000 * 2 ** i, 30000) + Math.random() * 250;
await new Promise((r) => setTimeout(r, espera));
}
}
}

feita: bool = False

id: int
tarefas: dict[int, Tarefa] = {}
proximo_id = 1

def listar() -> list[Tarefa]:

def criar(dados: TarefaIn) -> Tarefa:
global proximo_id
nova = Tarefa(id=proximo_id, **dados.model_dump())
tarefas[nova.id] = nova
proximo_id += 1
return nova

Figura 19.1 — O API Gateway é o ponto único de entrada. Cada microsserviço tem seu próprio banco de dados.
Como a portaria de um condomínio, o gateway identifica quem chega, barra quem não deve entrar, controla o

O app de celular precisa de pouco dado e economiza bateria; o painel web mostra tudo de uma vez. Em vez de
uma API genérica que agrada ninguém, cria-se um back-end específico para cada front-end, que agrega e
adapta as chamadas aos microsserviços.

📘 SLI, SLO e SLA
SLI (indicador): o que você mede. Ex.: "% de requisições respondidas em menos de 300 ms".
SLO (objetivo): a meta interna. Ex.: "99,9% das requisições abaixo de 300 ms".
SLA (acordo): a promessa contratual ao cliente, com multa se descumprida. Ex.: "disponibilidade de
99,5% ao mês".
Por que p95 e não a média? Porque a média esconde os usuários que sofrem. Se 5% das chamadas levam
4 segundos, a média pode parecer ótima.
Ferramentas comuns: OpenTelemetry (padrão aberto para coletar tudo), Prometheus + Grafana, Jaeger,
Datadog, New Relic, Elastic. Exponha também um endpoint de saúde, como 
GET /health , para
balanceadores e orquestradores saberem se a instância está viva.

🌍 A economia das APIs
Algumas das empresas de tecnologia mais valiosas do mundo têm uma API como produto principal: Stripe
(pagamentos), Twilio (SMS, voz, WhatsApp), Google Maps Platform, AWS (praticamente tudo é uma
chamada de API), Plaid (dados financeiros). Os modelos de cobrança mais comuns são por chamada, por
volume mensal, freemium e por receita compartilhada.
🤖 APIs na era da inteligência artificial
Os grandes modelos de linguagem (LLMs) são, eles mesmos, consumidos via API: você envia um texto em uma
requisição HTTP e recebe a resposta gerada, muitas vezes em streaming via SSE. Mas a grande mudança é o
caminho inverso: a IA chamando as suas APIs.
1. Tool use / function calling: você descreve suas funções (nome, parâmetros em JSON Schema) e o modelo
decide quando chamá-las. Ex.: o usuário pergunta "qual o endereço do CEP 01001-000?" e o modelo pede
para executar buscar_cep("01001000") .
2. MCP (Model Context Protocol): um protocolo aberto que padroniza como aplicações de IA se conectam
a ferramentas e fontes de dados. Em vez de cada integração ser feita sob medida, um "servidor MCP"
expõe ferramentas que qualquer cliente compatível consegue descobrir e usar — algo como uma "tomada
universal" para IAs.
